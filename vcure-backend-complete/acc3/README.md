## 2. Environment constraint

This sandbox has no outbound network access, so:
- `npm install` cannot reach the npm registry (Prisma CLI/client are **not**
  installed here).
- `npx prisma migrate dev` cannot run against a live PostgreSQL instance.

**What this means for you:** `prisma/schema.prisma` is the real, authoritative
schema — it was written by hand against the Engineering Bible and passed a
static self-consistency check (see §4). `prisma/migrations/000000000000_init/migration.sql`
was generated by a purpose-built parser (`scripts/generate_migration.py`)
that translates the schema to PostgreSQL DDL, since the real Prisma migration
engine wasn't available to generate it directly. **Once you have DB
connectivity, regenerate the canonical migration:**

```bash
npm install
cp .env.example .env   # fill in real DATABASE_URL / DIRECT_URL
npx prisma migrate dev --name init
```

If the real Prisma-generated SQL differs from `000000000000_init/migration.sql`
in any way (it may — Prisma's migration engine has more nuance than a
hand-rolled parser, e.g. around default value semantics for `@default(uuid())`,
which Prisma actually generates client-side rather than as a DB default),
**trust the Prisma-generated migration** and discard the hand-rolled one from
this init run.

### Domain coverage (Sec. 32 Database Domain Map)

Authentication · User · Health · Medical · Nutrition · Recipe · Recommendation
· Tracking · Education · Marketplace · AI · Administration — all 11 domains
from `03_DATABASE_ARCHITECTURE.md` Part 3B are modeled, plus the master/lookup
tables from Section 49 (Country, State, City, Language, Religion,
SubscriptionPlan; category tables are seeded per-domain).

### Rules applied throughout (traceable to Bible section numbers)

- **UUID PKs everywhere**, never auto-increment (Sec. 8) — `gen_random_uuid()`
  DB default, requires the `pgcrypto` extension (enabled by the migration).
- **Singular PascalCase models / camelCase columns** (Sec. 6–7).
- **Soft delete via `deletedAt`** on every user-generated table; nothing
  healthcare-related is ever hard-deleted (Sec. 11, Sec. 16).
- **Audit columns** `createdAt/updatedAt/deletedAt/createdBy/updatedBy` on
  every table that Sec. 12 marks as audit-critical, and on most others for
  consistency (Sec. 10).
- **History tables are append-only** — `BMIHistory`, `WeightTracking`,
  `SymptomHistory`, `RecommendationHistory`, `PromptHistory`, etc. have no
  `updatedAt`/soft-delete on the row itself; a new row is always inserted
  (Sec. 13, Sec. 48).
- **Cascade policy respects healthcare data** (Sec. 16): every FK from a
  medical/health table back to `User` uses `onDelete: Restrict`, not
  `Cascade` — deleting a user must go through the application's soft-delete
  flow, never a DB-level cascade delete of medical records. Pure operational
  child rows (e.g. `RecipeStep` under `Recipe`, `RolePermission` under
  `Role`) use `Cascade` since they have no independent lifecycle.
- **Enums replace repeated free text** (Sec. 22) — 28 enums covering gender,
  activity level, meal type, disease severity, goal type, subscription plan,
  role, account status, and more.
- **Files store URL/path/type/size only** (Sec. 23) — see
  `MedicalReportFile`; no binary blobs in Postgres.
- **Composite indexes** on `(userId, date)`-shaped query patterns per
  Sec. 20/52 (`daily_lifestyles`, `meal_plans`, `daily_summaries`, etc.).
- **Safety-critical diseases seeded with `isCritical=true`** — Chronic Kidney
  Disease, Cirrhosis/Fatty Liver Disease, Pregnancy, Gestational Diabetes,
  Celiac Disease — so the Safety Engine (a later step) can query by flag
  rather than by fragile name-matching, directly supporting Sec. 54
  Healthcare Safety Rules ("never ignore kidney disease / liver disease /
  pregnancy").

### Deliberate normalizations beyond the Bible's literal table list

The Bible lists `Micronutrient`, `Macronutrient`, `Vitamin`, `Mineral` as
domain tables without specifying how they attach to `Food`. Per Sec. 4
("No duplicated business data") and Sec. 55 Business Validation Rules, a
food-to-nutrient relationship needs a join table to stay normalized rather
than duplicating nutrient values as loose columns. Added `FoodMicronutrient`
as that join table. This is an extension, not a redesign — no existing table
from the Bible was renamed, removed, or restructured.
